# Measurement results, 2026-11-02

Four runs with the measurement mode of v0.9.x (`measure.md`), between the desktop
(DESKTOP-USHN7EU: RTX 5070 Ti, NVENC, DDA capture, 2560×1440 primary + 1920×1080 second
display) and the laptop (LAPTOP-AVOEN7VP: RTX 3050 Ti for decode and presentation, Intel
`hevc_qsv` for encode, GDI capture, 1920×1080), over Tailscale with the desktop on Wi-Fi behind a
VPN. Numbers are from the `report.md` tables; the per-second JSON files hold the rest.

| run | direction | screen | build | steps | state |
|---|---|---|---|---|---|
| 1 | desktop → laptop | 1080p (second display) | 0.9.0 | 24 | valid for GPU rows; still phase was 58 fps of identical frames, CPU rows measured a lock bug |
| 2 | laptop → desktop | laptop 1080p | 0.9.2 / 0.9.3 | 10 | 7 steps empty (4:4:4 stream), 2 as tiles |
| 3 | laptop → desktop | laptop 1080p | 0.9.3 | 10 | H.265 flows; QSV four frames late; freezes after any loss; 2 as tiles |
| 4 | desktop → laptop | 1440p (primary) | 0.9.4 | 24 | all valid |

## 1. The pipeline, stage by stage

GPU decode and GPU presentation on the laptop; the desktop encodes with NVENC. Medians in the
detail and motion phases.

| stage | desktop → laptop, 1080p (run 1) | desktop → laptop, 1440p (run 4) | laptop → desktop, 1080p (run 3) |
|---|---|---|---|
| capture | DDA, 58–60 fps | DDA, 58–60 fps | GDI, **30 fps** (BitBlt + compare ≈ 33 ms) |
| encode | NVENC AV1/HEVC 3.6–4.6 ms | 7–9 ms | QSV HEVC 5.6–5.8 ms, but **four frames late** (async depth 4): 133 ms at 30 fps, 4 s at 1 fps |
| rtt (clock probes) | 12–13 ms | 12–14 ms | 12–13 ms |
| decode | D3D11VA 5.5 ms (software HEVC 2.5–4) | D3D11VA 8 ms (software HEVC 6–7) | D3D11VA 3.0–3.3 ms (software 2.8–3.3) |
| draw | 0.8 ms | 1.3–1.9 ms | 0.9–1.0 ms |
| **latency p50, capture → presented** | **17–22 ms** | **25–31 ms** | **152–165 ms** (≈ 20 ms + the QSV queue) |

The CPU paths (run 4, laptop, 1440p): software decode + GPU draw = 58 fps, latency 25 ms;
GPU decode + CPU draw = 26 ms per frame, 36 fps, latency 64 ms; both on the CPU = 34–38 fps,
latency 60 ms. The CPU presentation path is the fallback only.

## 2. The link

Desktop → laptop. "Actual" is the video rate received in the motion phase.

| cap | run 1 (1080p) | run 4 (1440p) |
|---|---|---|
| 2–10 Mb/s | 0 % loss, stall < 90 ms | 0 % loss |
| 15 Mb/s | 9.4 Mb/s actual, 1.35 % loss, one 747 ms stall | 11.2 Mb/s actual, 0 % loss |
| 20 Mb/s | 10.9 Mb/s actual, 2 % loss (10 % in one 15 s window) | 6.8 Mb/s actual, 5–6 % loss, 152 frames lost, rtt 12 → 35 ms, 2–4 keyframes/s |

The usable ceiling is about **12 Mb/s**; above it loss grows with bitrate and rtt rises, which is
congestion. Laptop → desktop (run 3) carried 6 Mb/s of motion at the 15 Mb/s cap with 0 % loss;
the 20 Mb/s step froze for the reason in §4, not for the link.

Two events in run 1 did not fit the bitrate: a 15 s window at about 75 % loss, and 9 s during
which no media datagram arrived while the host kept sending 58 fps and the control channel sat at
12 ms rtt. They were about five minutes apart, the rhythm of the hiccups seen in earlier live
sessions. The path (Tailscale direct or relay) during such an event has not been checked.

## 3. Settings, measured

| setting | effect |
|---|---|
| 30 fps cap | holds exactly (30.1 fps); latency +3–5 ms |
| parity 5 vs 30 % at 6 Mb/s | no loss either way; 30 % takes 23 % of the video bits (4.65 → 3.74 Mb/s) |
| scale 75 % | latency 40 ms vs 28 at full size; detail phase 53 fps — the host downscales on the CPU |
| scale 50 % | decode 4 ms, draw 0.4 ms, latency 21–24; detail phase 45–48 fps, same cause |
| AV1 vs H.265 (NVENC) | same latency and decode time; H.265 stays far under its budget on this content (motion 1–3.5 Mb/s at any cap), AV1 spends it; picture quality by eye not compared yet |
| tiles at 20 Mb/s | 1–4 fps at 1080p, 1–2 fps at 1440p: last resort only |

## 5. Open

- **Laptop tiles fallbacks**: in runs 2 and 3 the 2 and 4 Mb/s steps started as H.265 and
  switched to tiles mid-session (an encode error). Only the laptop's `service.log` says why.
- **Keyframe storms**: at 20 Mb/s every lost frame became a keyframe request, 2–4 keyframes a
  second, each making the next loss likelier (run 4, av1-20).
- **Total silence**: the viewer cannot tell that media stopped arriving (run 1, 9 s); it waits.
- **Host downscale on the CPU** caps the scale rungs at 45–53 fps and adds latency.
- **GDI capture at 30 fps** on the laptop (BitBlt + compare of 8 MB per frame).
- **Quality by eye** in the detail phase, AV1 vs H.265 and per bitrate, has not been judged.
- **The five-minute events** have not been tied to a cause.

## 6. What the data says about the controllers

The fixed runs never ran the ladder. Together with the adaptive sessions of 2026-11-02 (before
0.9.0):

1. Loss that grows with bitrate comes with rising rtt and latency (run 4, 20 Mb/s: rtt 12 → 35,
   p50 28 → 58). Random Wi-Fi loss comes with flat latency (run 1 at 6 Mb/s, and the earlier
   adaptive sessions where dropping rungs changed nothing). A loss-only second should count as
   🔴 only when latency or rtt rose as well.
2. Keyframe requests need a rate limit under loss, and an unanswered request needs a timeout
   into a visible status.
3. Raises should be gated on the same 30 s loss window as the backstop; in the adaptive sessions
   a backstop drop was undone 15 s later.
4. The scale rungs should leave the ladder until the host scales on the GPU.
5. Parity at the 5–10 % floor is enough on a clean link; the controller already stays there.
6. The default top of 20 Mb/s is above this link's ceiling of about 12; the ladder exists to find
   that, provided 1 and 3 keep it from hunting.
